# general.md — 프로젝트 정의 & 개요

## 1. 프로젝트 개요

| 항목 | 내용 |
|------|------|
| 프로젝트명 | 파일업로드 확장자 차단 서비스 |
| 한 줄 정의 | 관리자가 설정한 확장자 차단 정책이 실제 파일 업로드에 강제 적용되는 시스템 |
| 평가 초점 | 화면 구현 자체보다 **파일 업로드를 다룰 때의 기획/보안/예외 관점 고려 깊이**를 중점 평가 |

---

## 2. 배경

파일 업로드 기능은 웹 서비스에서 흔히 제공되지만, 실행 파일(`exe`, `sh` 등)이 서버에 업로드·실행될 경우 보안 사고로 이어질 수 있다. 이를 방지하기 위해 **확장자 기반 업로드 차단 정책**을 관리자가 설정하고, 그 정책이 실제 업로드 처리 로직에 강제되는 기능이 필요하다.

---

## 3. 목적

1. 파일 업로드 차단 정책을 **실제로 동작하는 형태**로 구현하고 배포한다.
2. 정책 수립·구현 과정에서 고려한 **기획/보안/예외/운영 관점**을 문서로 남긴다.

---

## 4. 프로젝트 범위 (Scope)

### 4-1. 포함 범위 (In Scope) — 최소 구현
- 확장자 차단 정책 관리 화면
  - 고정 확장자 체크박스 (`bat`, `cmd`, `com`, `cpl`, `exe`, `scr`, `js`) — DB 저장/유지
  - 커스텀 확장자 추가/삭제 — 최대 200개, 항목당 최대 20자
- 실제 파일 업로드 시 위 정책을 서버 사이드에서 강제 적용
- 정책 저장용 DB 테이블 설계
- EC2 배포

### 4-2. 파일 검증 레이어 (5단계, 상세는 `spec.md`에서 정의)
1. **확장자 검사** — 정책(고정/커스텀) 기반 1차 필터, 대소문자/이중확장자 정규화 포함
2. **MIME 검사** — `Content-Type` 기반 보조 필터 (클라이언트 제공값이라 신뢰도 낮음, 확장자와 불일치 시 의심 처리)
3. **Magic Number 검사** — 파일 바이트 시그니처 기반 실제 파일 타입 검증 (핵심 레이어)
4. **Parser 기반 실제 구조 검증** — 파일을 실제로 열어 구조 검증 (예: office 문서의 zip 구조, 이미지 디코딩 가능 여부). **비용이 크므로 대표 타입 위주로 구현, 나머지는 확장 가능성으로 문서화**
5. **악성코드 검사 (ClamAV)** — Docker로 ClamAV 컨테이너를 띄워 연동. **동기 방식**으로 구현 (업로드 요청 처리 중 스캔 → 결과에 따라 즉시 성공/차단 응답). 

> 검증 순서는 비용이 저렴한 순(1→2→3)으로 먼저 걸러내고, 무거운 검증(4, 5)은 뒤에 배치하는 파이프라인 구조를 기본으로 한다. 전 레이어를 동기 방식으로 순차 처리한다.

### 4-3. 선택 범위 (시간 부족 시 문서화만 해도 무방)
- 이중 확장자 / 대소문자 / 유니코드 정규화 처리 상세
- 정책 변경 이력(Audit Log)
- 동시 편집 정합성, 모니터링/로깅 체계
- 화이트리스트 방식으로의 확장 가능성
- Parser 구조 검증의 전체 확장자 커버리지
- ClamAV 비동기 처리(임시 저장 → 스캔 → 결과 반영) 전환

## 5. 요구사항 요약

### 5-1. 기능 요구사항 (Functional) — `function.md`에서 상세화
- 정책 관리(고정/커스텀 확장자 CRUD)
- 업로드 시 정책 검증 및 차단/허용 처리

### 5-2. 비기능 요구사항 (Non-Functional)
| 구분 | 요구사항 |
|------|------|
| 보안 | 서버 사이드 검증 필수 (클라이언트 검증은 보조 수단) |
| 데이터 정합성 | 정책 변경 시 즉시 DB 반영, 새로고침 후에도 상태 유지 |
| 가용성 | 면접 당일 실제 접속 가능한 배포 상태 유지 |
| 성능 | 최대 200개 커스텀 확장자 조회 시에도 지연 없이 동작 |
| 문서화 | 스키마/API/검증 규칙/디자인/AI 활용 기록 전부 문서로 존재 |

## 6. 이해관계자 & 사용 시나리오

| 역할 | 설명 |
|------|------|
| 관리자(사용자) | 확장자 차단 정책을 설정/해제하는 주체 |
| 업로더(사용자) | 실제로 파일을 업로드하는 주체 (관리자와 동일인일 수도 있음) |

**대표 시나리오**
1. 관리자가 정책 화면에서 `exe` 체크 + 커스텀 확장자 `sh` 추가 → 저장
2. 사용자가 `malware.exe` 업로드 시도 → 서버가 차단, 사유 표시
3. 사용자가 `report.pdf` 업로드 → 정상 처리

## 8. 문서 체계 (본 4-문서 세트 간 관계)

```
general.md   → 프로젝트 정의, 목적, 요구사항 (본 문서)
function.md  → 화면/기능 단위 상세 (정책 관리, 업로드 처리 등)
```

- 과제 원본 문서의 "3. 기획/개발 고려사항"은 `CONSIDERATIONS.md`로 별도 관리하되, 필요한 항목은 `spec.md`/`design.md`에도 구체화하여 반영한다.

## 10. 가정 및 제약사항

- 별도 언급이 없는 한 단일 관리자 기준으로 설계하며, 다중 사용자 동시 편집 정합성은 "고려사항"으로만 문서화한다. (구현 여부는 스택 확정 후 재검토)
- 파일은 **EC2 로컬 디스크**에 저장한다 (애플리케이션 정적 리소스 경로 밖의 별도 경로, 예: `/home/ec2-user/uploads`).
  ClamAV 동기 스캔이 같은 인스턴스 내 로컬 소켓 통신을 전제로 하므로, 파일 저장소를 S3 등으로 분리하면 스캔을 위해 재다운로드가 필요해져 동기 처리의 이점이 사라진다고 판단해 로컬 디스크로 결정.
  저장 시 원본 파일명 대신 UUID 사용, 실행 권한 제거(chmod) 적용.
- EC2 인스턴스에서 Spring 애플리케이션과 ClamAV 컨테이너(Docker)를 함께 운영하므로, **인스턴스 스펙(메모리/CPU)이 ClamAV 리소스 사용량을 감당할 수 있는지** 사전 확인이 필요하다.
- ClamAV 악성코드 검사는 **동기 방식**으로 구현한다 (구현 단순성 우선). 업로드 요청 처리 흐름 안에서 스캔이 끝난 뒤 결과를 응답하며, 대용량/다중 파일 시 응답 지연은 알려진 한계로 `CONSIDERATIONS.md`에 기록한다.
