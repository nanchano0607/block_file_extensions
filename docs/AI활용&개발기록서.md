| Phase 2 Office 구조 검사 | Apache POI 5.5.1 | docx/xlsx/pptx 파일을 실제로 열어 OOXML 구조의 정상·손상 여부를 검증하는 데 사용 |

## 4-3. 판단 근거 회고 (AI 결과물 검증)

### 1. 그대로 쓴 것 (Accepted)
- 5단계 검증 파이프라인의 **처리 순서 원칙**(비용 저렴한 검증 먼저, 무거운 검증 나중) — 타당한 설계 원칙이라 판단해 수정 없이 채택.
- design.md 작성 시 AI가 자체적으로 내린 **F1-2(체크박스 자동저장) 최종 결정과 그 근거**(항목 수가 적어 일괄저장 이점이 낮음) — 별도 반려 없이 그대로 채택. 앞서 여러 차례 AI의 임의 판단을 반려/수정했던 것과 달리, 이번엔 근거가 합리적이라고 판단해 검증 후 승인.
- Phase 1 테스트 DB로 H2 대신 **Testcontainers의 실제 MySQL**을 사용하자는 제안 — Flyway V1의 MySQL 전용 DDL과 UNIQUE 제약을 운영 DB와 같은 조건에서 검증할 수 있다는 근거가 타당해 채택.
- ClamAV 장애 시 **fail-closed**로 처리하자는 제안 — 파일 검사 시스템의 목적상 가용성보다 미검사 파일을 허용하지 않는 것이 우선이라는 근거가 타당해 채택. 사용자에게는 내부 연결 정보 대신 일반화된 5xx 메시지만 반환하도록 제한.
- 업로드 성공 DB 기록 실패 시 **이미 저장한 파일을 삭제**하자는 보상 처리 — 파일만 남고 DB 행이 없는 불일치를 방지한다는 목적이 명확해 채택.

### 2. 고쳐 쓴 것 (Modified)
- **ClamAV 처리 방식**: AI는 처음에 "응답지연 우려로 비동기(임시저장→스캔→반영) 검토"를 제안했으나, 과제 성격(인터뷰용 과제, 시간 제약)을 고려해 **동기 방식 + 구현 단순화**로 직접 결정해 반영 지시.
- **general.md 범위**: AI가 초안 작성 시 AI 활용 관련 내용을 general.md(시스템 정의 문서)에 섞어 넣었으나, 문서 역할이 맞지 않다고 판단해 제거 지시.
- **고정 확장자 모델**: 초기 구현은 DB 문자열을 기준으로 했으나, 7개 값이 시스템에서 고정된 집합이라는 점을 근거로 사용자가 enum 관리를 제안. 엔티티 PK까지 enum으로 바꾸는 대신 Hibernate 7 제약을 확인한 후 DB 매핑은 문자열로 유지하고 애플리케이션 정책 기준만 enum으로 관리하도록 절충.
- **오류 관리 방식**: 초기에는 `BusinessException` 생성 시 HTTP 상태와 메시지를 직접 전달했으나, 사용자가 공통 `ErrorCode` 파일로 분리하도록 지시. 이후 상태·메시지를 enum 한곳에서 관리하고 서비스와 정규화 로직은 오류 코드만 선택하도록 수정.
- **매직넘버 미탐지 처리**: AI의 최초 구현은 등록한 7개 시그니처 중 어느 것에도 해당하지 않는 파일까지 차단했으나, txt처럼 고유 시그니처가 없는 정상 형식도 존재한다는 사용자 지적에 따라 "알려진 시그니처가 감지됐고 후보 확장자와 불일치하는 경우"만 차단하도록 수정.
- **Parser 지원 범위**: AI가 문서의 대표 형식 원칙에 따라 Office 3종과 jpg/jpeg/png만 구현했으나, 사용자가 매직넘버 목록에는 GIF가 있는데 Parser 목록에는 빠진 정합성 문제를 질문. ImageIO가 GIF를 지원하므로 추가 비용이 작다고 판단해 GIF를 포함하도록 수정.
- **업로드 차단 예외 정보**: 초기 파이프라인은 모든 실패를 일반 `BusinessException`으로 즉시 던져 `matched_extension`과 실패 단계 정보가 사라졌음. 사용자가 문제를 반복해서 지적해 `UploadBlockedException`이 카테고리·상세 로그·매칭 확장자를 운반하고 최상위 서비스가 DB 기록 후 예외를 다시 던지는 구조로 수정.
- **multipart 크기 설정**: 최초에는 Spring 상한과 업무 상한을 모두 10MB로 설정했으나, 이 경우 요청 파싱 단계에서 먼저 거절되어 실패 이력을 저장할 수 없음을 15단계에서 재확인. 업무 기준 10MB는 유지하면서 Spring 보호 상한을 11/12MB로 분리해 관측성과 자원 보호를 절충.

### 3. 버린 것 & AI 오류 수정 (Rejected & Caught Errors)
- **섹션 번호 중복 오류**: AI가 general.md 4번 항목을 정리하면서 "4-3(선택범위)"과 "4-3(제외범위)"를 중복 번호로 생성 → 직접 발견하고 수정 지시.
- **논리적 모순 방치**: ClamAV를 실제로 도입하기로 확정했음에도 AI가 만든 "제외 범위" 섹션에는 여전히 "바이러스 백신 연동 제외"라는 문구가 남아있었음 → 앞뒤가 맞지 않는 부분을 직접 짚어 삭제 지시.
- **과잉 차단 정책 (근거 없는 일반화)**: AI가 dotfile(`.env` 등)을 "확장자 없는 파일"과 동일하게 취급해 차단하도록 제안했으나, 이는 **파일명(레이블)과 실제 위험성을 혼동한 판단**이었음. `.env`라는 이름 자체가 위험을 의미하지 않는다는 근거를 들어 반려하고, 일반 확장자와 동일하게 정책 대조만 하도록 수정.
- **알고리즘의 자체 모순(AI가 스스로 포착 후 방치한 허점)**: AI가 제안한 4단계 확장자 판별 알고리즘은 "`.`이 하나도 없는 파일(`Makefile`)도 조각 1개로 처리되어 정책에 없으면 통과될 수 있다"는 허점을 AI 스스로 "주의" 문구로 남겼으나, 이를 바로 고치지 않고 "spec.md에서 추가 결정 필요"로 미뤄둔 상태였음 → 이 허점을 방치하지 않고 "`.` 유무를 최우선으로 먼저 판별"하는 5단계 알고리즘으로 직접 재작성해 반영 지시. **AI가 문제를 인지하고도 결론까지 밀어붙이지 않은 부분을 사용자가 마무리 지은 사례.**
- **문서 간 정합성 누락 (function.md ↔ spec.md)**: function.md에서 이미 "이중 확장자는 모든 후보를 각각 검사한다"고 확정했음에도, AI가 spec.md의 DB 스키마를 설계할 때는 `upload_file.extension`을 단일 값 컬럼으로만 설계해 두 문서 간 논리가 어긋났음. AI가 새 문서를 만들 때 이전 문서에서 확정한 규칙과의 정합성을 스스로 검증하지 않는다는 패턴을 확인 → 컬럼을 `extension_candidates`(후보 전체 보존) + `matched_extension`(차단 유발 값)로 분리하도록 직접 지적해 수정.
- **복잡성을 늘린 형식 통일 리팩터링**: 생성자 형식을 `@RequiredArgsConstructor`로 통일하는 변경을 적용했으나 현재 단계에서는 설정값 주입과 서비스 의존성 흐름을 오히려 읽기 어렵게 만듦. 사용자가 결과를 검토한 뒤 즉시 롤백을 지시했고, 이후 단순한 수동 생성자를 유지함.
- **확장자 후보 0개 분기 누락**: 문서에는 `...`처럼 빈 문자열 제거 후 조각이 하나도 없으면 차단한다고 명시돼 있었지만 최초 코드에는 해당 분기가 빠졌음. 사용자가 spec.md의 정확한 문구를 다시 제시해 누락을 발견했고 테스트와 함께 보완함.
- **동시성 락의 첫 수정 시도 자체 결함(AI가 스스로 작성한 테스트로 자기 오류를 포착한 사례)**: 커스텀 확장자 200개 한도의 TOCTOU 레이스를 고치면서 처음엔 `synchronized`만 걸었으나, 직접 작성한 동시성 통합 테스트(`CountDownLatch`로 두 요청 동시 발사)를 돌려보니 여전히 `[201, 201]`로 레이스가 재현됐음. `@Transactional`의 실제 커밋은 메서드가 끝나 락이 풀린 뒤에 일어나기 때문에 `synchronized`가 아무 효과가 없었던 것 — 이를 별도 지적 없이 스스로 진단해 `TransactionTemplate`으로 락을 쥔 채 커밋까지 마치도록 재수정함. **사용자가 반려한 것이 아니라, AI가 검증 테스트를 통해 자기 수정의 불완전함을 스스로 발견하고 고친 사례.**

> 공통적으로, AI가 생성한 산출물을 그대로 채택하지 않고 **① 과제 원문 요구사항과의 정합성, ② 문서 내부의 논리적 일관성, ③ 문서 간(예: function.md ↔ spec.md) 상호 정합성, ④ 보안·정책 판단의 실제 근거 유무**를 기준으로 매번 검수한 뒤 반영 여부를 결정함. 특히 문서 개수가 늘어날수록(③) AI가 앞서 확정한 내용을 다음 문서에 자동으로 반영하지 못하는 경우가 반복적으로 나타나, **새 문서를 만들 때마다 이전 확정 문서를 다시 첨부하거나 명시적으로 대조 확인을 요구하는 습관**이 필요하다는 점을 확인함.

| 단계 | 구현 결과 | 검증 방법 |

| 3단계 매직넘버 | EXE/ELF/ZIP/PDF/JPG/PNG/GIF 시그니처 대조 | 위장 실행파일 차단, 정상 시그니처 통과, 시그니처 없는 txt 통과 검증 |

Phase 2에서는 각 검사기를 독립 구현한 뒤 `UploadService`에서 동일한 `requestId`로 순차 연결했다. 사용자 응답에는 일반화된 메시지만 노출하고, DB에는 감사에 필요한 카테고리와 확장자 후보를, 서버 로그에는 구체적인 판단 근거를 분리해 남겼다. 최초 구현 뒤에도 Parser 폴리글랏 우회, 예외 발생 시 차단 기록 누락, 고아 파일 정리 로그 누락, ClamAV 쓰기 무한 대기, MIME 로그 전용 원칙 훼손, 후보별 반복 쿼리를 테스트로 재현한 후 보완했다.

## 4-6. Phase 1·2 코드 리뷰 및 결함 수정 요약

Codex로 Phase 1·2를 완료한 뒤, **구현에 참여하지 않은 Claude Code로 전체 코드를 교차 검증**했다. `/code-review` 스킬(high 강도)을 업로드 파이프라인·정책 모듈 두 갈래 병렬 서브에이전트로 실행해 실제 소스를 전량 읽고 11건을 도출했으며, 전부 실패 테스트(Red)로 먼저 재현한 뒤 수정(Green)했다.

| # | 결함 | 파일 | 수정 |
| :--- | :--- | :--- | :--- |
| 1 | `BusinessException` 외 예외(검증 오류, DB 예외 등)가 공통 응답 규격을 깨고 그대로 노출됨 | `GlobalExceptionHandler` | `MethodArgumentNotValidException`/`MethodArgumentTypeMismatchException`(400), `DataAccessException`/`Exception` 전체(500) 폴백 핸들러 추가 |
| 2 | 이중 확장자 중 첫 번째로 지원되는 후보만 Parser 구조 검증을 받아, 폴리글랏 파일이 뒤에 숨은 위험 구조를 우회할 수 있음 | `ParserStructureInspector` | 지원되는 **모든** 후보를 검사하도록 수정 |
| 3 | DB 저장 실패 등 `BusinessException`이 아닌 예외가 발생하면 차단 감사 기록이 전혀 남지 않음 | `UploadService` | catch 범위를 `RuntimeException`으로 확장, `BlockReasonCategory.UNKNOWN_ERROR`로 기록 |
| 4 | 고아 파일 정리(`deleteQuietly`) 실패 시 로그가 전혀 남지 않아 추적 불가 | `FileStorageService` | 실패 시 `log.error`로 경로·예외 기록 |
| 5 | `Socket#setSoTimeout`은 쓰기에는 적용되지 않아 clamd가 응답을 멈추면 무한 대기 가능 | `ClamAvScanner` | 소켓 쓰기를 가상 스레드로 분리, `Future.get(timeout)`으로 실제 타임아웃 적용 |
| 6 | 200개 한도 체크(count)와 저장(insert)이 원자적이지 않아 동시 요청이 한도를 넘길 수 있음(TOCTOU) | `PolicyCommandService` | `synchronized`+`TransactionTemplate`으로 락 안에서 커밋까지 완료하도록 수정(최초 `synchronized`만으로는 불충분했음을 자체 테스트로 발견 후 재수정) |
| 7 | Tika가 손상된 입력에 `RuntimeException`을 던지면 "MIME은 절대 차단 안 함" 원칙이 깨짐 | `MimeTypeInspector` | `catch(IOException)` → `catch(Exception)`으로 확장 |
| 8 | ClamAV 응답을 바이트 단위로 읽어 불필요한 syscall 반복 | `ClamAvScanner` | `BufferedInputStream` 적용 |
| 9 | 확장자 후보마다 정책 조회 쿼리를 개별 실행(N+1성 패턴) | `ExtensionPolicyValidator`, 리포지토리 | 배치 `IN` 조회 2회로 축소, 반환 타입도 엔티티 대신 확장자 문자열 목록으로 단순화 |
| 10 | 모든 차단 지점이 `UploadBlockedException`만 던지는데도, 도달 불가능한 `ErrorCode→카테고리` 폴백 switch가 남아있어 드리프트 위험 | `UploadService` | 죽은 코드 제거, `UNKNOWN_ERROR`로 통일 |
| 11 | `DataIntegrityViolationException`을 전부 "중복 확장자"로 매핑해, 무관한 DB 오류도 잘못된 메시지를 반환할 수 있음 | `PolicyCommandService` | 실제 unique 제약(`uk_custom_extension_extension`) 메시지 매칭 여부로 정밀화 |
