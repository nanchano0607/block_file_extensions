## 1. 검증/보안 관점 (원문 3-1)

### 1-1. 확장자만 믿어도 되는가
**판단**: 믿지 않는다. 확장자(1단계) → MIME(2단계, 참고용) → **매직넘버(3단계, 최종 판단)** → 구조검증(4단계) → 악성코드검사(5단계)로 이어지는 5단계 검증을 구축했다.

**근거**: 확장자와 MIME은 둘 다 클라이언트가 주장하는 값(파일명, `Content-Type` 헤더)이라 위조가 쉽다. 서버가 파일의 실제 바이트를 직접 열어 판단하는 매직넘버부터 신뢰할 수 있다고 판단해, 확장자 정책을 통과했더라도 매직넘버에서 위험 시그니처(예: `4D 5A`, Windows 실행파일)가 발견되면 최종적으로 차단한다.

**구현 여부**: 구현 (`spec.md` 4-3)

---

### 1-2. 대소문자 / 이중 확장자
**판단**: 대소문자는 비교 전 소문자로 정규화. 이중/다중 확장자(`file.exe.txt`)는 "마지막 확장자만" 보지 않고, `.` 기준으로 **전체 분리 후 모든 조각을 확장자 후보로 검사**한다.

**근거**: 마지막 확장자만 검사하면 `malware.exe.txt`처럼 위험 확장자를 중간에 숨겨 우회할 수 있다. 반대로 파일명 전체를 하나의 문자열로 보고 "exe가 포함되는지" 검사하면 `my.company.report.pdf` 같은 정상 파일까지 과잉 차단될 수 있어, 점(`.`) 단위로 정확히 분리한 조각만 확장자 후보로 취급했다.

**세부 알고리즘 (spec.md 4-1, function.md F2-2)**
1. 파일명에 `.`이 하나도 없으면 → 확장자 없는 파일로 차단 (`Makefile`, `README` 등)
2. `.` 기준 전체 분리 → 빈 문자열 제거
3. 남은 조각이 없으면 → 차단
4. 남은 조각 각각을 정책과 대조, 하나라도 매칭되면 차단

**구현 여부**: 구현

---

### 1-3. 확장자 없는 파일 / 점으로 시작하는 파일(.env) / 매우 긴 파일명

| 케이스 | 판단 | 근거 |
|---|---|---|
| 확장자 없는 파일 (`Makefile`) | **차단** | 정책(블랙리스트)을 적용할 대상 자체가 없는 "판별 불가능"한 입력이며, 판별 불가능한 입력에는 보수적으로 안전한 기본값(차단)을 택했다. 전체 시스템은 블랙리스트(위험한 것만 차단, default 허용) 철학인데 이 지점만 예외적으로 화이트리스트처럼 동작함을 인지하고 있다. |
| `.env` 등 점으로 시작하는 파일 | **차단하지 않음** (일반 확장자와 동일하게 정책 대조) | 처음에는 "환경변수 등 민감정보가 있어 위험하다"는 이유로 차단을 고려했으나, 이는 파일명(레이블)과 실제 위험성을 혼동한 판단이었다. 사용자가 업로드하는 `.env`는 서버 자체의 설정파일과 무관하며(UUID로 저장되어 실제 경로에 영향 없음), 이름이 `.env`라는 사실만으로 위험하다고 볼 근거가 없다고 재검토해 결정을 뒤집었다. |
| 매우 긴 파일명 | **미구현, 위험만 인지** | `original_filename` 컬럼(VARCHAR 255)을 넘는 파일명이 들어오면 DB 저장 단계(INSERT)에서 실패하는데, 이 시점은 이미 디스크에 UUID 파일명으로 저장을 마친 뒤라 **디스크에는 파일이 남고 DB에는 기록이 없는 불일치**가 생길 수 있다. 정규화 단계 앞에서 길이(255자) 초과 시 조기 차단하는 검사를 추가해야 한다고 판단했으나, 최소 구현 범위(A/B)에는 없는 방어 로직이라 이번 과제에서는 우선순위를 낮게 두고 구현하지 않았다. |

**구현 여부**: 확장자 없는 파일/dotfile 처리는 구현, 파일명 길이 제한은 **미구현** (원인·대응 방안만 문서화)

---

### 1-4. 확장자 입력값 검증 (정규화)
**판단**: 커스텀 확장자 등록 시 ① 앞뒤 공백 제거 ② 선행 `.` 제거 ③ 소문자 변환 ④ 영문 소문자+숫자만 허용(그 외 특수문자/공백/유니코드는 거부) ⑤ 길이 1~20자로 정규화한다.

**근거**: 등록 시점의 정규화 규칙과, 업로드 시 판별 시점의 정규화 규칙이 일치하지 않으면(예: 등록은 대소문자 구분 없이 했는데 판별은 구분해서 함) 정책이 실제로 작동하지 않는 상황이 생긴다. 두 시점의 규칙을 동일하게 맞췄다.

**유니코드 확장자에 대한 별도 판단**: 유니코드(전각문자 등) 확장자를 판별 시 특별 취급하지 않기로 했다. 등록 자체를 막지 않는 이상, 등록되지 않은 유니코드 값을 임의로 차단하는 것은 일관성 없는 과잉 차단이라 판단했다 (`.env` 판단과 같은 원칙 적용).

**구현 여부**: 구현 (`spec.md` 4-1, 6)

---

### 1-5. 서버사이드 검증의 필요성
**판단**: 클라이언트 체크는 UX 개선 목적으로만 사용하고(빠른 피드백), 최종 판단은 항상 서버가 내린다.

**근거**: 클라이언트 체크는 브라우저 개발자도구나 직접 API 호출(Postman/curl 등)로 손쉽게 우회 가능하다. 특히 파일 크기 초과는 클라이언트 단계에서 업로드 자체를 막지만(서버 호출이 무의미하므로), 확장자 차단 여부는 클라이언트가 들고 있는 정책이 최신이 아닐 수 있어(예: 관리자가 방금 정책을 변경) **경고만 하고 업로드 자체는 막지 않는다** — 서버가 최종 판단을 내릴 여지를 항상 열어둔다. (`design.md` 2-1)

**구현 여부**: 구현

---

### 1-6. 업로드 파일 크기 제한 / 파일 개수 제한

**파일 크기 제한 — 판단**: 10MB로 확정.

**근거**: 처음 50MB를 고려했으나, ClamAV를 동기 방식으로 처리하기로 한 결정과 EC2 무료 티어의 제한된 리소스(CPU 1개, RAM 1GB 안팎)를 고려했을 때 대용량 파일은 응답 지연과 메모리 부담을 키운다고 판단해 10MB로 낮췄다. 이 과제는 실 서비스가 아닌 평가/데모 목적이라 대용량 지원의 실익도 적다.

**파일 개수 제한 — 판단**: 요청(API 호출) 1건당 파일 1개만 허용한다. `POST /api/upload`는 `multipart/form-data`에 단일 필드 `file`만 받도록 설계했고, 여러 파일을 동시에 선택해도 프론트에서 순차적으로 개별 요청을 보내는 구조다. 동일 사용자가 짧은 시간에 여러 번 반복 업로드하는 것을 막는 별도의 rate limit은 두지 않았다.

**근거**: 한 요청에 여러 파일을 담으면 ① 일부 파일만 차단됐을 때 부분 성공을 어떻게 응답할지(예: 3개 중 1개만 악성코드 탐지) 응답 스키마가 복잡해지고, ② ClamAV 동기 스캔이 파일마다 순차 실행되어 요청 하나의 응답 지연이 파일 수에 비례해 커진다. 과제의 최소 구현 범위(B)가 "정상 파일은 업로드 성공 처리"라고만 명시할 뿐 다중 파일 업로드를 요구하지 않아, 단일 파일 요청으로 단순화하는 쪽이 검증 로직의 명확성과 응답 시간 예측 가능성 면에서 낫다고 판단했다. 짧은 시간 내 반복 요청 자체를 막는 rate limit(예: IP/세션당 분당 N회)은 필요성은 인지하지만 단일 관리자·평가용 과제 규모에서는 실익이 적어 고려사항으로만 남긴다.

**구현 여부**: 파일 크기 제한은 구현(`spec.md` 4-0, Spring 설정 + 애플리케이션 레벨 이중 검증), 파일 개수 제한은 API 구조(요청당 1개)로 구현, 반복 요청 rate limit은 미구현(근거만 문서화)

---

### 1-7. 저장 시 원본 파일명 사용 위험
**판단**: 원본 파일명을 저장 경로에 사용하지 않고, `UUID.randomUUID()` 기반 파일명으로 저장. 저장 위치는 애플리케이션 정적 리소스 경로 바깥(`/home/ec2-user/uploads/`), 저장 직후 `chmod 600`으로 실행 권한 제거.

**근거**: 원본 파일명을 그대로 쓰면 경로 조작(path traversal), 파일명 충돌, 웹에서 직접 URL로 접근 가능해지는 위험이 있다. 정적 리소스 경로 안에 두면 Spring Boot가 자동으로 웹에 노출시키므로, 완전히 분리된 경로를 사용했다.

**구현 여부**: 구현 (`spec.md` 5)

---

### 1-8. MIME 타입 스푸핑
**판단**: MIME 불일치는 **차단 근거로 사용하지 않는다.** 로그(WARN 레벨)로만 기록하고, 최종 판단은 매직넘버(3단계)에 위임한다.

**근거**: `Content-Type` 헤더는 브라우저가 자동 생성하거나, curl 등으로 임의 조작 가능한 값이라 확장자와 마찬가지로 신뢰도가 낮다. 신뢰도 낮은 값을 차단 근거로 쓰기보다, 모니터링용 참고 정보로만 활용하는 것이 논리적으로 더 일관된다고 판단했다.

**구현 여부**: 구현 (`spec.md` 4-2)

## 2. 정책/데이터 관점 (원문 3-2)

### 2-1. 고정 확장자와 커스텀 확장자가 겹칠 때
**판단**: 커스텀 확장자 등록 시 고정 확장자 7개와 중복되면 서버에서 거부(`409`).

**근거**: 같은 확장자가 두 테이블에 동시에 존재하면, 한쪽에서 체크를 해제했는데 다른 쪽엔 여전히 남아있는 정합성 문제가 생긴다. 하나의 확장자는 반드시 하나의 저장소(고정 또는 커스텀)에서만 관리되도록 등록 자체를 막았다.

**구현 여부**: 구현

---

### 2-2. 정책 변경 이력/감사
**판단**: 필요성은 인지했으나, 이번 과제에서는 **선택 구현**으로 분류했다. 테이블 스키마(`extension_policy_history`)는 설계해뒀으나 실제 연동 코드는 시간에 따라 구현 여부를 결정한다.

**근거**: 여러 관리자가 정책을 바꿀 경우, 언제 무엇이 바뀌었는지 추적할 수단이 없으면 장애 원인 파악이 어렵다는 점에서 필요성은 명확하다고 판단했다. 다만 과제 최소 요구사항에는 없는 항목이라 구현 우선순위를 낮게 잡았다.

**구현 여부**: 스키마만 준비 (`spec.md` 2-5), 실제 구현은 미정

---

### 2-3. 200개 / 20자 제한의 근거와 초과 시 UX
**판단**: 200개/20자는 과제 원문에 명시된 값을 그대로 채택. 이 제한은 DB 스키마 레벨(CHECK 제약, 트리거)로 강제하지 않고 **애플리케이션 레벨에서 검사**한다. 초과 시 프론트 입력창/버튼을 비활성화하고 인라인 에러를 표시한다.

**근거**: 200이라는 값은 운영 정책상 나중에 바뀔 수 있는 값이라, DB 스키마에 하드코딩하면 유지보수가 어려워진다. 200개 수준에서는 `COUNT(*)` 조회 비용도 무시할 만해 애플리케이션 레벨 검사로 충분하다고 판단했다.

**구현 여부**: 구현 (`spec.md` 2-3)

---

### 2-4. 대량 확장자 조회/저장 시 성능·인덱스
**판단**: `custom_extension.extension`에 UNIQUE 인덱스, `upload_file`에 `created_at`/`status` 인덱스를 부여했다.

**근거**: 최대 200행 규모에서는 인덱스 없이도 성능 문제가 없지만, 업로드마다 매칭 조회가 발생하는 컬럼(`extension`)과 시간이 지나며 계속 쌓이는 이력 테이블(`upload_file`)에는 명시적으로 인덱스를 걸어두는 것이 원칙적으로 맞다고 판단했다.

**구현 여부**: 구현 (`spec.md` 7)

---

## 3. UX/예외 관점 (원문 3-3)

### 3-1. 차단 시 사용자에게 보여줄 메시지
**판단**: "무엇이, 왜 막혔는지"를 카테고리 수준으로만 알려준다 (예: "허용되지 않는 파일 형식입니다", "악성코드가 탐지되었습니다"). 어느 검증 단계에서, 어떤 값이 왜 불일치했는지의 세부 사유는 노출하지 않고 서버 로그에만 남긴다.

**★ 이 판단 과정에서 발견한 요구사항 간 충돌** (섹션 5-4 참고)

**구현 여부**: 구현 (`function.md` F2-2, `spec.md` 3-3)

---

### 3-2. 로딩/에러/네트워크 실패 상태 처리
**판단**: 모든 비동기 동작(저장/추가/삭제/업로드)은 **로딩 → 성공/실패**의 단순한 상태만 다룬다. 디바운스, 오프라인 감지, 단계별 진행률 표시 같은 정교한 처리는 이 과제 규모에 비해 과하다고 판단해 넣지 않았다.

**근거**: 화면이 2개뿐인 작은 과제에서 지나치게 정교한 상태 관리는 구현 대비 효과가 낮고, 오히려 "왜 이렇게까지 했는지" 설명하기 어려운 군더더기가 될 수 있다고 판단했다.

**구현 여부**: 구현 (`design.md`)

---

### 3-3. 저장 실패 시 화면 상태와 DB 상태의 일관성
**판단**: 낙관적 업데이트(클릭 즉시 화면 반영)를 사용하되, 실패 시 반드시 이전 상태로 롤백한다.

**근거**: 화면과 DB가 다른 상태로 어긋나면 사용자가 실제 정책 상태를 오인할 수 있다. 즉각적인 반응성(낙관적 업데이트)과 정합성(실패 시 롤백)을 함께 가져가는 절충안을 택했다.

**구현 여부**: 구현 (`design.md` 1-3, 1-4, 1-5)

---

### 3-4. 접근성/반응형 (선택)
**판단**: 기본 시맨틱 HTML만 지키고, 심화 접근성(`aria-live` 등)·반응형은 시간 여유에 따라 구현.

**근거**: 과제 원문에서도 선택 항목으로 명시되어 있어, 필수 기능 완성도를 우선하고 남는 시간에 반영하기로 했다.

**구현 여부**: 선택 (미구현 시 본 항목으로 근거 대체)

---

## 4. 운영 관점 (원문 3-4)

### 4-1. 새로고침/동시 편집 시 정합성
**판단**: 단일 관리자 기준으로 설계했다. 다중 사용자 동시 편집 정합성은 이번 과제에서 구현하지 않고 고려사항으로만 남긴다.

**근거**: 과제 요구사항에 다중 사용자/동시 편집 시나리오가 명시되지 않았다. 실제 서비스로 확장한다면 낙관적 락(버전 컬럼) 또는 마지막 쓰기 우선 정책이 필요하다고 판단했으나, 이번 스코프에서는 우선순위가 낮다.

**구현 여부**: 미구현, 근거만 문서화

---

### 4-2. 로그/모니터링 관점에서 무엇을 남길 것인가
**판단**: `upload_file` 테이블에 모든 업로드 시도(성공/차단)를 기록한다. 차단된 경우 일반화된 카테고리(`block_reason_category`)만 저장하고, 상세 판단 근거(어떤 확장자가 매칭됐는지 등)는 별도 컬럼(`extension_candidates`, `matched_extension`)에 내부 감사용으로만 남긴다.

**근거**: 이 테이블은 과제 최소 요구사항에는 없지만, "로그/모니터링 관점에서 무엇을 남길 것인가"라는 원문 질문에 대한 직접적인 답으로 추가했다. DB가 유출되더라도 검증 로직의 세부 동작이 노출되지 않도록, 사용자에게 보여주는 것과 같은 수준의 정보만 카테고리 컬럼에 저장하고 상세 정보는 분리했다.

**구현 여부**: 구현 (`spec.md` 2-4)

---

### 4-3. 향후 확장 가능성
**판단**: 현재는 블랙리스트(위험한 확장자만 차단) 방식이며, 화이트리스트(허용 목록만 통과) 방식으로 전환 가능성을 열어두었다. 정책 변경 이력, 다중 사용자 정책 분리도 향후 확장 지점으로 문서화했다.

**근거**: 과제 원문이 예시로 든 "화이트리스트 방식 전환"에 대한 고려. 현재 스키마(`fixed_extension_policy`, `custom_extension`)는 화이트리스트 전환 시에도 큰 구조 변경 없이 `is_blocked` 의미를 반전하는 정도로 대응 가능하다고 판단했다.

**구현 여부**: 설계만 (문서화)

---

## 5. ★ 원문에 없는, 스스로 발견한 고려사항

과제 원문이 "여기 없는 고려사항을 스스로 찾아내는 것을 특히 높게 본다"고 명시한 부분에 대한 답이다.

### 5-1. 매직넘버가 없는 파일 형식의 한계 (js, sh, bat)
텍스트 기반 스크립트 파일(`js`, `sh`, `bat` 등)은 바이너리 파일과 달리 고유한 매직넘버(바이트 시그니처)가 없다. 이 경우 5단계 검증 중 3단계(매직넘버)가 사실상 무력화되며, **1단계(확장자 검사)가 이런 파일 형식에 대한 유일한 방어선**이 된다는 한계를 스스로 발견했다. 매직넘버 검사의 실질적 효용은 "바이너리 실행파일이 문서 확장자로 위장한 경우"를 잡아내는 데 있다는 점을 명확히 인지하고 문서화했다.

### 5-2. Parser 구조 검증(4단계)의 필요성 — 매직넘버만으로는 부족한 이유
매직넘버는 파일의 **앞부분 몇 바이트만** 검사하므로, 정상 파일 헤더 뒤에 악성 페이로드를 붙이는 폴리글랏(polyglot) 공격은 탐지하지 못한다는 한계를 인지하고, 대표 타입(ZIP 기반 오피스 문서, 이미지)에 대해 실제로 파일을 끝까지 열어보는 구조 검증 단계를 추가로 설계·구현했다.

### 5-3. 악성코드 검사(5단계)의 필요성과 구현 방식 선택
형식이 정상이어도 내부에 악성 매크로/스크립트가 있을 수 있다는 점을 고려해 ClamAV를 도입했다. 최초에는 VirusTotal(외부 API) 연동을 검토했으나, 비동기 폴링 구조 전체를 새로 설계해야 하는 구현 복잡도 문제를 발견하고 ClamAV(동기, 로컬 소켓 통신)로 전환했다 — 구현 난이도와 보안 수준 사이의 트레이드오프를 스스로 비교해 결정했다.

### 5-4. 필수 요구사항 간의 충돌 발견 — "명확한 사유"와 "검증 로직 비노출"
과제 최소 구현 범위(B)는 "차단 대상 파일 업로드 시 명확한 사유와 함께 거부"를 요구하지만, 3-1(보안 관점)의 서버사이드 검증 원칙을 지키려면 검증 로직의 세부 동작(어느 단계에서 왜 막혔는지)을 노출하면 안 된다. **이 둘이 서로 충돌한다는 점을 스스로 발견**했고, "무엇이 문제였는지의 큰 범주"는 명확히 알려주되 "어느 단계·어떤 값이 불일치했는지"의 세부는 숨기는 절충안(카테고리 메시지)으로 양쪽 요구사항을 최대한 만족시키는 지점을 택했다.

### 5-5. `.env` 차단 여부에 대한 최초 판단 오류를 스스로 정정
개발 초기에는 dotfile(`.env` 등)을 "확장자 없는 파일"과 동일하게 취급해 차단하는 방향으로 설계했으나, 이는 **파일명(레이블)과 실제 위험성을 혼동한 과잉 차단**이었다. `.env`라는 이름 자체가 위험을 의미하지 않으며, 사용자가 업로드하는 동명의 파일은 서버 자체의 설정파일과 무관하다는 점을 재검토해 판단을 뒤집었다.

### 5-6. 확장자 판별 알고리즘의 자체 허점을 발견 및 수정
초기에 설계한 이중확장자 처리 알고리즘은 "점(`.`)이 하나도 없는 파일(`Makefile`)도 분리 시 조각 1개로 처리되어, 정책에 등록되지 않은 이상 그대로 통과된다"는 허점이 있었다. 이를 방치하지 않고, "`.` 유무를 최우선으로 먼저 판별"하는 알고리즘으로 재작성해 반영했다. `Makefile`, `README`, `.env`, `abc.`, `....abc`, `...` 등 경계 케이스를 표로 정리해 알고리즘 하나로 모든 케이스가 일관되게 처리되는지 직접 검증했다.

## 6. 기술 스택 선택에 대한 판단 (참고)

세부 근거는 `general.md`에 있으나, 이 과제의 평가 취지("AI가 준 코드를 검증 없이 그대로 쓰지 않는 것")와 직결되는 판단이라 요약한다.

**Backend를 Node.js가 아닌 Spring Boot로 결정한 이유**: JD(채용공고) 요건만 보면 Node.js도 충분히 유효한 선택이었으나, 본인이 검증할 수 없는 언어로 AI가 짜준 코드를 그대로 쓰는 것은 이 과제가 "가장 피해야 할 것"으로 명시한 상황과 정확히 일치한다고 판단해, 본인이 직접 코드를 읽고 검증할 수 있는 Spring Boot로 스택을 결정했다.
