## 1. 검증/보안 관점 (원문 3-1)

### 1-1. 확장자만 믿어도 되는가
**판단**: 믿지 않는다. 크기(0단계) → 확장자(1단계) → MIME(2단계, 참고용) → **매직넘버(3단계, 알려진 시그니처 판정)** → 구조검증(4단계) → 악성코드검사(5단계)로 이어지는 총 6단계 검증을 구축했다.

**근거**: 확장자와 요청 MIME은 둘 다 클라이언트가 주장하는 값(파일명, `Content-Type` 헤더)이라 위조가 쉽다. 따라서 서버가 실제 바이트를 읽는 매직넘버·Parser·ClamAV를 뒤에 배치했다. 다만 매직넘버 검사는 등록된 7종의 시그니처만 판별하므로 인식하지 못한 형식은 통과시킨다. 즉 매직넘버 하나가 모든 형식의 최종 판정 수단인 것은 아니며, **알려진 바이너리 시그니처와 확장자 후보의 불일치를 잡는 핵심 레이어**로 사용한다. 최종 허용 여부는 이후 구조검증과 악성코드검사까지 모두 통과한 뒤 결정한다.

**구현 여부**: 구현 (`spec.md` 4장)

---

### 1-2. 대소문자 / 이중 확장자
**판단**: 대소문자는 비교 전 소문자로 정규화. 이중/다중 확장자(`file.exe.txt`)는 "마지막 확장자만" 보지 않고, 현재 구현에서는 `.` 기준으로 **전체 분리 후 모든 조각을 확장자 후보로 검사**한다. 이 방식이 basename까지 후보에 포함해 오탐을 만들 수 있다는 남은 한계는 섹션 5-9에 별도로 기록했다.

**근거**: 마지막 확장자만 검사하면 `malware.exe.txt`처럼 위험 확장자를 중간에 숨겨 우회할 수 있다. 반대로 파일명 전체를 하나의 문자열로 보고 "exe가 포함되는지" 검사하면 `my.company.report.pdf` 같은 정상 파일까지 과잉 차단될 수 있어, 점(`.`) 단위로 정확히 분리한 조각만 확장자 후보로 취급했다.

**세부 알고리즘 (spec.md 4-1, function.md F2-2)**
1. 파일명에 `.`이 하나도 없으면 → 확장자 없는 파일로 차단 (`Makefile`, `README` 등)
2. `.` 기준 전체 분리 → 빈 문자열 제거
3. 남은 조각이 없으면 → 차단
4. 남은 조각 각각을 정책과 대조, 하나라도 매칭되면 차단

**구현 여부**: 구현

---

### 1-3. 확장자 없는 파일 / 점으로 시작하는 파일(.env) / 매우 긴 파일명

| 케이스 | 판단 | 근거 |
|---|---|---|
| 확장자 없는 파일 (`Makefile`) | **차단** | 정책(블랙리스트)을 적용할 대상 자체가 없는 "판별 불가능"한 입력이며, 판별 불가능한 입력에는 보수적으로 안전한 기본값(차단)을 택했다. 전체 시스템은 블랙리스트(위험한 것만 차단, default 허용) 철학인데 이 지점만 예외적으로 화이트리스트처럼 동작함을 인지하고 있다. |
| `.env` 등 점으로 시작하는 파일 | **차단하지 않음** (일반 확장자와 동일하게 정책 대조) | 처음에는 "환경변수 등 민감정보가 있어 위험하다"는 이유로 차단을 고려했으나, 이는 파일명(레이블)과 실제 위험성을 혼동한 판단이었다. 사용자가 업로드하는 `.env`는 서버 자체의 설정파일과 무관하며(UUID로 저장되어 실제 경로에 영향 없음), 이름이 `.env`라는 사실만으로 위험하다고 볼 근거가 없다고 재검토해 결정을 뒤집었다. |
| 매우 긴 파일명 | **미구현, 위험만 인지** | `original_filename`(VARCHAR 255) 또는 파일명에서 만든 `extension_candidates`(VARCHAR 100)의 한도를 넘으면 DB 기록이 실패할 수 있다. 성공 이력 INSERT 실패 시 이미 저장한 UUID 파일은 보상 삭제하므로 고아 파일은 남지 않지만, 같은 긴 값을 사용한 차단 이력 INSERT도 실패할 수 있어 **사용자는 500 응답을 받고 DB에는 시도 이력이 남지 않는 감사 공백**이 생긴다. 서비스 진입 직후 원본 파일명과 후보 문자열 길이를 검증하거나, 감사용 컬럼 크기·저장 방식을 재설계해야 한다. |

**구현 여부**: 확장자 없는 파일/dotfile 처리와 성공 이력 저장 실패 시 파일 보상 삭제는 구현. 파일명·후보 문자열 길이의 조기 제한은 **미구현** (원인·대응 방안만 문서화)

### 1-4. 확장자 입력값 검증 (정규화)
**판단**: 커스텀 확장자 등록 시 ① 앞뒤 공백 제거 ② 선행 `.` 제거 ③ 소문자 변환 ④ 영문 소문자+숫자만 허용(그 외 특수문자/공백/유니코드는 거부) ⑤ 길이 1~20자로 정규화한다.

**근거**: 등록 값은 DB UNIQUE 제약과 업로드 정책 비교에 직접 쓰이므로 동일 의미의 값(`EXE`, `.exe`, ` exe `)이 여러 형태로 저장되지 않도록 엄격하게 제한했다. 등록과 업로드 판별 양쪽 모두 공백 제거·소문자 변환은 적용하지만, 업로드 파일명은 외부 입력이므로 등록 값과 달리 영문/숫자 형식을 강제로 요구하지 않는다.

**유니코드 확장자에 대한 별도 판단과 한계**: 유니코드(전각문자 등) 확장자를 업로드 시 자동 차단하지 않고, 다른 검증 단계까지 통과하면 허용한다. 다만 현재 커스텀 정책에는 영문/숫자만 등록할 수 있으므로 관리자가 특정 유니코드 확장자만 선택해 차단할 수는 없다. 이는 블랙리스트의 기본 허용 원칙을 따른 결과지만, 실제 운영에서 유니코드 정책 관리가 필요해지면 등록 규칙과 Unicode 정규화(NFKC 등)를 함께 재설계해야 한다.

**구현 여부**: 구현 (`spec.md` 4-1, 6)

### 1-5. 서버사이드 검증의 필요성
**판단**: 클라이언트 체크는 UX 개선 목적으로만 사용하고(빠른 피드백), 최종 판단은 항상 서버가 내린다.

**근거**: 클라이언트 체크는 브라우저 개발자도구나 직접 API 호출(Postman/curl 등)로 손쉽게 우회 가능하다. 특히 파일 크기 초과는 클라이언트 단계에서 업로드 자체를 막지만(서버 호출이 무의미하므로), 확장자 차단 여부는 클라이언트가 들고 있는 정책이 최신이 아닐 수 있어(예: 관리자가 방금 정책을 변경) **경고만 하고 업로드 자체는 막지 않는다** — 서버가 최종 판단을 내릴 여지를 항상 열어둔다. (`design.md` 2-1)

**구현 여부**: 구현

---

### 1-6. 업로드 파일 크기 제한 / 파일 개수 제한

**파일 크기 제한 — 판단**: 업무 기준 10MB로 확정.

**근거**: 처음 50MB를 고려했으나, ClamAV를 동기 방식으로 처리하고 Spring·MySQL·ClamAV를 같은 EC2에서 실행하는 구조에서는 대용량 파일이 응답 지연과 메모리 부담을 키운다고 판단해 10MB로 낮췄다. 실제 t3.small(2GB RAM) 최초 기동에서도 ClamAV 시그니처 적재 중 OOM이 발생해 2GB Swap을 추가한 뒤 정상화했다. 안정적인 운영은 t3.medium(4GB) 이상을 권장하며, 이 과제는 평가/데모 목적이라 대용량 지원의 실익도 적다.

**Spring 보호 상한과의 분리 (구현 중 발견하고 수정한 부분)**: 최초에는 Spring의 multipart 상한과 업무 기준 상한을 모두 10MB로 동일하게 설정했다. 그런데 이렇게 하면 10MB를 초과하는 요청이 **Spring의 요청 파싱 단계에서 애플리케이션 코드(`UploadService`)에 도달하기도 전에 거절**되어, "왜 차단됐는지"를 `upload_file` 테이블에 `SIZE_EXCEEDED`로 기록하는 감사 로직 자체가 실행되지 못하는 문제를 실제 구현·테스트 과정에서 발견했다. 이를 해결하기 위해 **업무 기준(10MB)과 Spring 보호 상한(파일 11MB, 요청 전체 12MB)을 분리**했다 — Spring은 명백히 비정상적인 크기(예: 100MB)만 요청 단계에서 즉시 차단해 자원을 보호하고, 10~11MB 사이의 "업무 기준 초과" 케이스는 애플리케이션 코드까지 도달시켜 정상적으로 `SIZE_EXCEEDED` 이력을 남기도록 했다.

**파일 개수 제한 — 판단**: 요청(API 호출) 1건당 파일 1개만 허용한다. `POST /api/upload`는 `multipart/form-data`에 단일 필드 `file`만 받도록 설계했고, 여러 파일을 동시에 선택해도 프론트에서 순차적으로 개별 요청을 보내는 구조다. 동일 사용자가 짧은 시간에 여러 번 반복 업로드하는 것을 막는 별도의 rate limit은 두지 않았다.

**근거**: 한 요청에 여러 파일을 담으면 ① 일부 파일만 차단됐을 때 부분 성공을 어떻게 응답할지(예: 3개 중 1개만 악성코드 탐지) 응답 스키마가 복잡해지고, ② ClamAV 동기 스캔이 파일마다 순차 실행되어 요청 하나의 응답 지연이 파일 수에 비례해 커진다. 과제의 최소 구현 범위(B)가 "정상 파일은 업로드 성공 처리"라고만 명시할 뿐 다중 파일 업로드를 요구하지 않아, 단일 파일 요청으로 단순화하는 쪽이 검증 로직의 명확성과 응답 시간 예측 가능성 면에서 낫다고 판단했다. 짧은 시간 내 반복 요청 자체를 막는 rate limit(예: IP/세션당 분당 N회)은 필요성은 인지하지만 단일 관리자·평가용 과제 규모에서는 실익이 적어 고려사항으로만 남긴다.

**구현 여부**: 파일 크기 제한(업무 기준 + Spring 보호 상한 이원화)은 구현(`spec.md` 4-0, Spring 설정 + 애플리케이션 레벨 이중 검증), 파일 개수 제한은 API 구조(요청당 1개)로 구현, 반복 요청 rate limit은 미구현(근거만 문서화)

### 1-7. 저장 시 원본 파일명 사용 위험
**판단**: 원본 파일명을 저장 경로에 사용하지 않고, `UUID.randomUUID()` 기반 파일명으로 저장한다. 로컬 기본 경로는 `./uploads`, 운영 컨테이너 내부 경로는 `/app/uploads`이며 Docker named volume `uploads_data`에 영속화한다. 두 경로 모두 애플리케이션 정적 리소스 밖이고, 저장 직후 권한을 `600`으로 제한한다.

**근거**: 원본 파일명을 그대로 쓰면 경로 조작(path traversal), 파일명 충돌, 웹에서 직접 URL로 접근 가능해지는 위험이 있다. 정적 리소스 경로 안에 두면 Spring Boot가 자동으로 웹에 노출시키므로, 완전히 분리된 경로를 사용했다.

**구현 여부**: 구현 (`spec.md` 5)

---

### 1-8. MIME 타입 스푸핑
**판단**: MIME 불일치는 **차단 근거로 사용하지 않는다.** 로그(WARN 레벨)로만 기록하고, 실제 허용 여부는 매직넘버·Parser·ClamAV처럼 파일 내용을 직접 검사하는 후속 단계에 맡긴다.

**근거**: `Content-Type` 헤더는 브라우저가 자동 생성하거나, curl 등으로 임의 조작 가능한 값이라 확장자와 마찬가지로 신뢰도가 낮다. 신뢰도 낮은 값을 차단 근거로 쓰기보다, 모니터링용 참고 정보로만 활용하는 것이 논리적으로 더 일관된다고 판단했다.

**구현 여부**: 구현 (`spec.md` 4-2)

## 2. 정책/데이터 관점 (원문 3-2)

### 2-1. 고정 확장자와 커스텀 확장자가 겹칠 때
**판단**: 커스텀 확장자 등록 시 고정 확장자 7개와 중복되면 서버에서 거부(`409`).

**근거**: 같은 확장자가 두 테이블에 동시에 존재하면, 한쪽에서 체크를 해제했는데 다른 쪽엔 여전히 남아있는 정합성 문제가 생긴다. 하나의 확장자는 반드시 하나의 저장소(고정 또는 커스텀)에서만 관리되도록 등록 자체를 막았다.

**구현 여부**: 구현

---

### 2-2. 정책 변경 이력/감사
**판단**: 선택 범위였지만 최종 구현했다. `extension_policy_history`에 고정 확장자 차단 ON/OFF와 커스텀 확장자 추가/삭제를 기록하고, 최신순 페이지네이션 조회 API와 프론트 변경 이력 화면을 제공한다.

**근거**: 정책 변경 시점과 대상을 추적할 수 없으면 특정 파일이 과거에는 허용되고 현재는 차단되는 이유를 설명하기 어렵다. 단일 관리자를 가정해 `changed_by`는 제외했지만, 정책 종류·확장자·변경 행위·변경 시각은 보존한다. 정책 변경과 이력 저장을 같은 트랜잭션에 묶어 둘 중 하나만 반영되는 불일치도 방지했다.

**구현 여부**: 구현 (Flyway V2·V4, `GET /api/policy/history`, 프론트 페이지네이션 화면)

---

### 2-3. 200개 / 20자 제한의 근거와 초과 시 UX
**판단**: 200개/20자는 과제 원문에 명시된 값을 그대로 채택. 이 제한은 DB 스키마 레벨(CHECK 제약, 트리거)로 강제하지 않고 **애플리케이션 레벨에서 검사**한다. 초과 시 프론트 입력창/버튼을 비활성화하고 인라인 에러를 표시한다.

**근거**: 200이라는 값은 운영 정책상 나중에 바뀔 수 있는 값이라, DB 스키마에 하드코딩하면 유지보수가 어려워진다. 200개 수준에서는 `COUNT(*)` 조회 비용도 무시할 만해 애플리케이션 레벨 검사로 충분하다고 판단했다.

**동시성 처리 (구현 중 자체 발견 및 최종 개선)**: 최초에는 `synchronized` 키워드만 사용했으나, `@Transactional`의 실제 커밋이 메서드 종료(=JVM 락 해제) 이후에 일어나 동시성 테스트가 실패했다. 그다음 `TransactionTemplate`으로 JVM 락 안에서 커밋까지 마치도록 보완했지만 이 방식은 서버 인스턴스가 여러 대면 서로의 락을 공유하지 못한다. 최종적으로 전용 `policy_write_lock` 행을 만들고 `PESSIMISTIC_WRITE`(`SELECT ... FOR UPDATE`)로 잠근 뒤, 같은 트랜잭션 안에서 **락 획득 → 중복 검사 → count 검사 → insert → commit** 순서로 처리하도록 변경했다. 따라서 동일 MySQL을 사용하는 여러 애플리케이션 인스턴스에서도 200개 한도를 직렬화할 수 있다.

**구현 여부**: DB 비관적 락으로 구현 (`PolicyCommandService`, `PolicyWriteLockRepository`, Flyway V3)

---

### 2-4. 대량 확장자 조회/저장 시 성능·인덱스
**판단**: `custom_extension.extension`에 UNIQUE 인덱스, `upload_file`에 `created_at`/`status` 인덱스를 부여했다.

**근거**: 최대 200행 규모에서는 인덱스 없이도 성능 문제가 없지만, 업로드마다 매칭 조회가 발생하는 컬럼(`extension`)과 시간이 지나며 계속 쌓이는 이력 테이블(`upload_file`)에는 명시적으로 인덱스를 걸어두는 것이 원칙적으로 맞다고 판단했다.

**구현 여부**: 구현 (`spec.md` 7)

**구현 여부**: 구현 (`design.md` 1-3, 1-4, 1-5)

## 4. 운영 관점 (원문 3-4)

### 4-1. 새로고침/동시 편집 시 정합성
**판단**: 단일 관리자 기준으로 설계했다. 다중 사용자 동시 편집 정합성은 이번 과제에서 구현하지 않고 고려사항으로만 남긴다.

**근거**: 과제 요구사항에 다중 사용자/동시 편집 시나리오가 명시되지 않았다. 실제 서비스로 확장한다면 낙관적 락(버전 컬럼) 또는 마지막 쓰기 우선 정책이 필요하다고 판단했으나, 이번 스코프에서는 우선순위가 낮다. (다만 2-3의 200개 한도처럼, "동시 편집"이 아니라 "동시 요청으로 인한 레이스 컨디션"은 실제로 발생 가능함을 확인하고 별도로 수정했다.)

**구현 여부**: 미구현, 근거만 문서화

---

### 4-2. 로그/모니터링 관점에서 무엇을 남길 것인가
**판단**: 애플리케이션 업로드 파이프라인에 도달한 시도는 `upload_file` 테이블에 성공/차단 상태로 기록한다. 사용자 응답에는 일반화된 카테고리 메시지만 제공하지만, DB에는 내부 감사용 `extension_candidates`, `matched_extension`, `block_reason_category`를 저장한다. 각 검증 단계는 `requestId`(요청당 1회 생성)로 로그를 상관관계 지어 하나의 업로드 시도에 대한 0~5단계 흐름을 추적할 수 있게 했다.

**근거**: 이 테이블은 과제 최소 요구사항에는 없지만, "로그/모니터링 관점에서 무엇을 남길 것인가"라는 원문 질문에 대한 직접적인 답으로 추가했다. 사용자에게는 공격자가 세부 검증 규칙을 추론할 만한 값은 반환하지 않되, 운영자는 DB의 후보·매칭값과 서버 로그의 단계별 상세 사유로 장애와 차단 원인을 추적할 수 있도록 노출 범위를 분리했다. 따라서 DB 자체는 사용자 응답보다 상세한 내부 정보를 포함하며 접근 통제가 필요하다. Spring multipart 보호 상한을 초과해 요청 파싱 전에 거절된 요청, 잘못된 multipart 요청, 파일명·감사 컬럼 한도 때문에 기록 자체가 실패한 요청은 이 테이블에 남지 않을 수 있으므로 "모든 HTTP 업로드 시도"를 보장하는 구조는 아니다.

**구현 여부**: 구현 (`spec.md` 2-4)

---

### 4-3. 향후 확장 가능성
**판단**: 현재는 블랙리스트(위험한 확장자만 차단) 방식이며, 화이트리스트(허용 목록만 통과) 방식으로 전환 가능성을 열어두었다. 변경 이력은 구현을 완료했으며, 향후에는 변경 주체 기록과 다중 사용자별 정책 분리가 확장 지점이다.

**근거**: 과제 원문이 예시로 든 "화이트리스트 방식 전환"에 대한 고려다. 기존 확장자 테이블을 일부 재사용할 수는 있지만 `fixed_extension_policy.is_blocked`의 의미만 반전하면 끝나는 변경은 아니다. 커스텀 확장자 테이블의 의미, 기본 허용/차단 규칙, 정책 API·검증 쿼리·화면 문구·기존 데이터 마이그레이션을 함께 바꿔야 한다. 실제 전환 시에는 정책 모드(`BLACKLIST`/`WHITELIST`)를 별도로 두고 두 모드의 판정 로직과 이력을 명시적으로 관리하는 편이 안전하다.

**구현 여부**: 설계만 (문서화)

**다운로드/조회 기능 확장 시 재검토할 점 (스스로 발견)**: `upload_file` 테이블에는 의도적으로 다운로드 URL이나 전체 경로를 저장하지 않는다 — 지금은 업로드만 있고 파일을 다시 꺼내 보여주는 엔드포인트가 없으며(`spec.md` 5장), 저장 파일은 `chmod 600`으로 소유자만 접근 가능해 URL이 있어도 애초에 아무것도 가리키지 못한다. 실제 경로는 항상 `app.upload.directory`(고정 설정값) + `stored_filename`(행별 UUID)으로 재구성 가능하므로 매 행에 중복 저장할 이유도 없다. 다운로드 기능을 같은 애플리케이션 프로세스에 추가한다면 권한 `600`을 유지한 채 인증된 프록시 엔드포인트로 제공할 수 있다. 별도 프로세스가 같은 파일을 읽어야 할 때만 소유 그룹을 분리하고 `640`으로 완화할지 검토한다. 또한 원본 경로 직접 노출 금지, 접근 권한 검사, 응답 `Content-Disposition`의 `original_filename` 노출 여부(파일명 자체에 민감정보가 담길 수 있음)를 함께 결정해야 한다.

**구현 여부**: 미구현(현재 범위에 다운로드 기능 없음), 확장 시 고려사항만 문서화

---

### 4-4. EC2 자원과 ClamAV 기동 안정성
**판단**: Spring·MySQL·ClamAV·Nginx를 한 인스턴스에서 실행할 때는 t3.medium(4GB RAM) 이상을 안정 권장 사양으로 잡는다. t3.small(2GB RAM)을 사용한다면 2GB Swap을 필수 보완책으로 적용하고, t2/t3.micro(1GB)는 사용하지 않는다.

**근거**: 실제 t3.small 최초 배포에서 ClamAV가 시그니처 DB를 적재하던 중 OOM으로 `clamd`가 종료되어 컨테이너가 `unhealthy`가 되었고, 이에 의존하는 backend와 frontend까지 시작하지 못했다. 20GiB EBS 여유 공간과 RAM 부족은 별개의 문제였으며, 2GB Swap을 추가한 뒤 `oom=false`, `healthy`를 확인했다. Swap은 급격한 메모리 부족을 완화하는 안전망이지 RAM과 같은 성능을 제공하지 않으므로 운영 사양 자체를 낮추는 근거로 사용하지 않는다.

**구현 여부**: 운영 환경에 적용 및 `DEPLOYMENT.md`에 재현 절차 문서화

---

### 4-5. 공개 URL의 접근 통제와 비밀정보 관리
**판단**: Compose에서는 frontend Nginx의 80번 포트만 호스트에 publish하고 ngrok이 이 포트를 HTTPS로 터널링한다. MySQL(3306), ClamAV(3310), backend(8080)는 Docker 내부 네트워크에만 둔다. DB 비밀번호와 ngrok Authtoken은 Git에 커밋하지 않고 각각 권한을 제한한 `.env`와 ngrok 전용 설정에 저장한다.

**근거**: 현재 과제에는 사용자 인증·관리자 권한·업로드 rate limit이 없다. 따라서 ngrok URL을 아는 사람은 정책을 변경하거나 파일을 반복 업로드할 수 있으므로 이 주소는 평가 기간에만 제한적으로 공유하고, 종료 후 터널을 내리는 것이 안전하다. ngrok만 진입점으로 사용할 경우 EC2 보안 그룹의 80번 직접 인바운드도 열지 않아 우회를 막아야 한다. 실제 서비스로 확장한다면 정책 API 관리자 인증, 업로드 rate limit, 요청 크기·횟수 모니터링을 먼저 추가해야 한다.

**구현 여부**: 포트 격리와 비밀정보 분리는 구현. 애플리케이션 인증·rate limit은 과제 범위 밖으로 미구현

---

### 4-6. 영속 볼륨의 보존·백업·재배포 정책
**판단**: MySQL, ClamAV 시그니처, 업로드 파일을 각각 Docker named volume으로 분리해 컨테이너 교체 시에도 데이터를 유지한다. 프론트만 바뀐 경우 `--no-deps frontend`로 선택 배포해 정상 동작 중인 DB·ClamAV·backend를 재시작하지 않는다.

**근거**: 이미지와 컨테이너는 다시 만들 수 있지만 DB와 업로드 파일은 복구할 수 없는 상태 데이터다. 따라서 일반 재배포에서 `docker compose down -v`를 사용하지 않으며, 운영 전에 MySQL 덤프와 `uploads_data` 백업·복구 절차를 별도로 마련해야 한다. 현재는 파일 보존 기간과 자동 삭제 작업이 없어 반복 업로드 시 디스크가 계속 증가하는 한계도 있다. 또한 기본 이미지 태그 `latest`는 시점에 따라 다른 이미지를 받을 수 있으므로 장기 운영에서는 커밋 SHA나 버전 태그로 고정해야 한다.

**구현 여부**: named volume과 선택 배포는 구현. 정기 백업·보존 기간 삭제 작업·불변 이미지 태그 운영은 미구현

## 5. ★ 원문에 없는, 스스로 발견한 고려사항

과제 원문이 "여기 없는 고려사항을 스스로 찾아내는 것을 특히 높게 본다"고 명시한 부분에 대한 답이다.

### 5-1. 매직넘버가 없는 파일 형식의 한계 (js, sh, bat)
텍스트 기반 스크립트 파일(`js`, `sh`, `bat` 등)은 바이너리 파일과 달리 고유한 매직넘버(바이트 시그니처)가 없다. 이 경우 3단계(매직넘버)와 4단계(Parser 구조검증)를 적용하기 어렵기 때문에 **1단계 확장자 정책이 주된 형식 방어선**이 된다. 5단계 ClamAV가 알려진 악성 스크립트 시그니처를 탐지할 가능성은 있지만 모든 스크립트의 위험성을 보장해서 판정하지는 못한다. 매직넘버 검사의 실질적 효용은 "알려진 바이너리 형식이 다른 확장자로 위장한 경우"를 잡아내는 데 있다는 한계를 명확히 문서화했다.

### 5-2. Parser 구조 검증(4단계)의 필요성 — 매직넘버만으로는 부족한 이유
매직넘버는 파일의 **앞부분 몇 바이트만** 검사하므로 헤더만 정상이고 내부 구조가 손상된 파일을 판별할 수 없다. 이를 보완하기 위해 ZIP 기반 오피스 문서는 Apache POI로, 이미지는 ImageIO로 실제 파싱하는 구조 검증 단계를 추가했다. 이 단계는 손상되거나 해당 포맷으로 열 수 없는 파일을 차단하지만, Parser가 뒤에 붙은 데이터를 무시할 수도 있어 모든 폴리글랏(polyglot) 파일이나 정상 구조 안의 악성 내용을 탐지한다고 보장할 수는 없다. 알려진 악성 페이로드 탐지는 이후 ClamAV가 별도로 담당한다.

### 5-3. 악성코드 검사(5단계)의 필요성과 구현 방식 선택
형식이 정상이어도 내부에 악성 매크로/스크립트가 있을 수 있다는 점을 고려해 ClamAV를 도입했다. 최초에는 VirusTotal(외부 API) 연동을 검토했으나, 비동기 폴링 구조 전체를 새로 설계해야 하는 구현 복잡도 문제를 발견하고 Docker 내부 네트워크의 ClamAV에 TCP `INSTREAM`으로 동기 전송하는 방식으로 전환했다 — 구현 난이도와 보안 수준 사이의 트레이드오프를 스스로 비교해 결정했다.

### 5-4. 필수 요구사항 간의 충돌 발견 — "명확한 사유"와 "검증 로직 비노출"
과제 최소 구현 범위(B)는 "차단 대상 파일 업로드 시 명확한 사유와 함께 거부"를 요구하지만, 3-1(보안 관점)의 서버사이드 검증 원칙을 지키려면 검증 로직의 세부 동작(어느 단계에서 왜 막혔는지)을 노출하면 안 된다. **이 둘이 서로 충돌한다는 점을 스스로 발견**했고, "무엇이 문제였는지의 큰 범주"는 명확히 알려주되 "어느 단계·어떤 값이 불일치했는지"의 세부는 숨기는 절충안(카테고리 메시지)으로 양쪽 요구사항을 최대한 만족시키는 지점을 택했다.

### 5-5. `.env` 차단 여부에 대한 최초 판단 오류를 스스로 정정
개발 초기에는 dotfile(`.env` 등)을 "확장자 없는 파일"과 동일하게 취급해 차단하는 방향으로 설계했으나, 이는 **파일명(레이블)과 실제 위험성을 혼동한 과잉 차단**이었다. `.env`라는 이름 자체가 위험을 의미하지 않으며, 사용자가 업로드하는 동명의 파일은 서버 자체의 설정파일과 무관하다는 점을 재검토해 판단을 뒤집었다.

### 5-6. 확장자 판별 알고리즘의 자체 허점을 발견 및 수정
초기에 설계한 이중확장자 처리 알고리즘은 "점(`.`)이 하나도 없는 파일(`Makefile`)도 분리 시 조각 1개로 처리되어, 정책에 등록되지 않은 이상 그대로 통과된다"는 허점이 있었다. 이를 방치하지 않고, "`.` 유무를 최우선으로 먼저 판별"하는 알고리즘으로 재작성해 반영했다. `Makefile`, `README`, `.env`, `abc.`, `....abc`, `...` 등 경계 케이스를 표로 정리해 알고리즘 하나로 모든 케이스가 일관되게 처리되는지 직접 검증했다.

### 5-7. 감사 로그를 남기려면 검증 로직이 애플리케이션 코드까지 도달해야 한다는 제약 발견
파일 크기 제한(1-6)을 구현하던 중, Spring의 multipart 상한과 업무 기준 상한을 동일하게(10MB) 설정하면 초과 요청이 애플리케이션 코드(`UploadService`)에 도달하기 전에 프레임워크 단계에서 거절되어, **"왜 차단됐는지"를 감사 이력(`upload_file`)에 남기는 로직 자체가 실행되지 못하는 구조적 문제**를 실제 구현·테스트 과정에서 발견했다. "차단 사유를 기록하려면, 최소한 그 판단을 내리는 코드가 한 번은 실행되어야 한다"는 원칙을 근거로, 프레임워크 보호 상한(파일 11MB/요청 12MB)과 업무 기준 상한(10MB)을 분리해 명백히 비정상적인 크기만 프레임워크가 먼저 차단하고, 업무 기준 초과는 애플리케이션 코드가 판단하여 정상적으로 이력을 남기도록 설계를 수정했다.

### 5-8. 실제 파일로 검증한 "정책 미설정 + 형식 위장" 복합 시나리오
확장자 판별 알고리즘을 문서상의 경계 케이스(`Makefile`, `.env` 등)뿐 아니라, 실제 업무용 파일(예: 실제 hwp 문서, exe로 위장한 dmg 파일)로도 6단계 파이프라인 전체를 로그로 추적하며 검증했다. 그 결과:

- exe가 정책에서 unCheck(허용) 상태일 때, 실제로는 dmg인 파일에 `.exe` 확장자만 붙여 업로드하면 1단계(정책 미설정)뿐 아니라 3단계(dmg 시그니처가 등록된 7종에 없어 미탐지)·4단계(exe는 Parser 검사 대상이 아님)·5단계(형식 위장 자체는 악성코드가 아니므로 통과)까지 전부 통과되는 것을 실증적으로 확인했다.
- 이를 통해 "확장자 위장 방어(3~4단계)"와 "위험 확장자 자체를 정책으로 차단하는 것(1단계)"은 서로 다른 문제이며, 매직넘버/구조검증은 어디까지나 "안전하다고 주장하는 형식이 진짜인지"를 검증하는 것이지 관리자가 위험 확장자를 애초에 차단해두지 않은 실수까지 보완해주지는 않는다는 한계를 재확인했다.
- 과제 요구사항(고정 확장자 default unCheck)은 그대로 따르되, 이 리스크가 실재함을 실제 파일 테스트로 문서화해 남긴다.

### 5-9. 확장자 후보 추출 시 basename까지 후보가 되는 한계
현재 알고리즘은 파일명을 점(`.`)으로 전체 분리한 모든 비어 있지 않은 조각을 후보로 사용한다. 따라서 `malware.exe.txt`에서 중간의 `exe`를 찾아내는 장점이 있지만, 점이 하나뿐인 `exe.txt`에서도 실제 확장자가 아닌 basename `exe`까지 후보가 된다. `exe` 차단 정책이 켜져 있으면 이 정상 `.txt` 파일이 잘못 차단될 수 있으므로 이는 단순한 불필요 조회가 아니라 **오탐 가능성이 있는 판정 정확성 문제**다. 긴 basename은 `extension_candidates` VARCHAR(100) 한도를 넘겨 감사 이력 저장 실패를 유발할 수도 있다.

이 문제를 해결하려면 최소한 마지막 조각은 실제 확장자로 유지하면서, 첫 조각을 무조건 후보로 볼지 여부를 파일명 형태에 따라 구분해야 한다. 예를 들어 점이 하나면 마지막 조각만, 점이 둘 이상이면 중간 조각부터 마지막 조각까지 검사하는 방식은 `exe.txt` 오탐을 막으면서 `malware.exe.txt`의 `exe`를 탐지할 수 있다. `.env`, `abc.`, `....abc` 같은 경계 케이스까지 다시 테스트해야 하므로 현재 구현의 남은 한계로 명시하고 후속 개선 대상으로 둔다.

## 6. 기술 스택 선택에 대한 판단 (참고)

세부 근거는 `general.md`에 있으나, 이 과제의 평가 취지("AI가 준 코드를 검증 없이 그대로 쓰지 않는 것")와 직결되는 판단이라 요약한다.

**Backend를 Node.js가 아닌 Spring Boot로 결정한 이유**: JD(채용공고) 요건만 보면 Node.js도 충분히 유효한 선택이었으나, 본인이 검증할 수 없는 언어로 AI가 짜준 코드를 그대로 쓰는 것은 이 과제가 "가장 피해야 할 것"으로 명시한 상황과 정확히 일치한다고 판단해, 본인이 직접 코드를 읽고 검증할 수 있는 Spring Boot로 스택을 결정했다.
